# 跨宿主交付协议

## 目标

无论运行在 Codex、WorkBuddy、Claude Code、Cursor 或其他支持 Agent Skills 的宿主中，交付物都必须先是一个真实文件，再尽可能作为宿主原生附件或文件卡片出现。蓝色文字不等于附件，可点击承诺必须有宿主能力和实际文件共同支撑。

## 生成阶段

1. 在当前 workspace 的任务目录中生成文件，不写入临时聊天缓存目录。
2. 文件名优先使用短 ASCII 名称：`article-preview.html`、`article-gzh.html`、`article-source.md`、`title-strategy.md`。
3. HTML 内部资源使用相对路径；需要单文件预览时将必要样式和可嵌入资源放入同一 HTML。
4. 交付前检查每个文件存在、非空、可读。HTML 还要确认浏览器可打开、正文非空、预览按钮不会遮挡正文。

## 公众号四件套

公众号文章完成排版后，以下四件交付物全部为必选，不得按模型判断省略：

1. **标题策略 Markdown**：`title-strategy.md` 或 `标题策略.md`，至少含推荐/主标题、2 个备选标题和简短选择理由。
2. **正文 Markdown**：`article-source.md` 或 `正文.md`，保留可继续修改的文章原稿。
3. **公众号正文 HTML**：`article-gzh.html`，只含可粘贴到公众号编辑器的干净正文片段。
4. **复制预览 HTML**：`article-preview.html`，浏览器可打开，并含“复制到公众号”功能。

生成完成后必须运行：

```bash
python3 scripts/validate_delivery_bundle.py <交付目录> --platform 公众号
```

校验未通过时直接补齐或修复文件并重新检查，不能先向用户交付三件套。

## 附件优先级

1. 调用宿主提供的原生附件、文件卡片、artifact 或等价文件交付能力。
2. 公众号按复制预览 HTML、公众号正文 HTML、正文 Markdown、标题策略 Markdown 的顺序附上四个真实文件。
3. 最终回复中的说明与附件名称一一对应；不生成一个名字、附上另一个文件。
4. 若宿主能回读附件状态，确认消息中已出现文件卡片后再结束。

## 禁止做法

- 不把 Windows 或 macOS 本地绝对路径写成 Markdown 链接，例如 `[预览](D:\\work\\article.html)` 或 `[预览](/Users/name/article.html)`。
- 不把不存在的路径、旧文件、临时文件或仅在另一个环境存在的文件包装成蓝色链接。
- 不因链接文字显示为蓝色就声称“可以直接打开”。
- 不只交付公众号干净片段而遗漏可浏览的预览页。
- 不因标题策略已经出现在聊天文字里，就省略标题策略 Markdown 文件。

## 能力降级

宿主没有原生附件/文件卡片能力时：

1. 明确说明当前宿主不支持把本地文件作为可点击附件发送。
2. 以纯文本列出真实绝对路径、文件名和用途，不使用 Markdown 链接。
3. 给出最短打开方式，但不让用户误以为链接可点击。

能力降级是事实说明，不得掩饰。Skill 能统一交付决策，但不能替宿主凭空增加文件附件能力。
