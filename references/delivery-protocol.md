# 跨平台、跨宿主交付协议

## 目标

交付物由发布平台的真实编辑与发布方式决定，不把公众号四件套复制到所有平台。进入文件交付时，先保证标题和平台原生正文可直接使用；只有平台属性或用户要求涉及排版，才增加两个 HTML 文件。

无论运行在 Codex、WorkBuddy、Claude Code、Cursor 或其他宿主中，交付物都必须先是一个真实文件，再尽可能作为宿主原生附件或文件卡片出现。蓝色文字不等于附件，可点击承诺必须有宿主能力和实际文件共同支撑。

## 一、先做交付判断

内部记录：

```text
- 发布平台：
- 平台原生正文格式：Markdown / 纯文本 / HTML
- 是否需要排版：是 / 否
- 判断依据：平台必需 / 用户明确要求 / 系统自动匹配
- 复制目标：富文本 HTML / 平台纯文本 / Markdown
```

当用户没有指定时，按平台属性判断：

| 发布平台 | 平台原生正文 | 默认是否排版 | 交付规则 |
| :--- | :--- | :--- | :--- |
| 公众号 | Markdown 原稿 + 公众号富文本 | 是，必需 | 固定四件套 |
| 知乎 | 回答 / 专栏 Markdown 或纯文本 | 否 | 默认标题策略 + 知乎原文；要求预览时再加两个 HTML |
| 小红书 | 可直接发布的纯文本笔记 | 否 | 默认标题策略 + 笔记原文；要求手机卡片预览时再加两个 HTML，复制页复制纯文本 |
| 官网/网页 | Markdown 源稿 + 网页 HTML | 是 | 标题策略、网页源稿、干净网页 HTML、复制预览 HTML |
| 个人博客 | 取决于博客系统 | 条件式 | Markdown 博客默认两件；静态 HTML/排版要求时增加两个 HTML |

未知平台先判断它接收纯文本、Markdown、富文本还是网页文件。无法确认且用户也未要求排版时，优先交付标题策略和平台原生正文，不机械生成 HTML。

知乎和小红书不能直接用表格中的默认值静默执行。用户未说明排版需求时，先询问“是否需要 HTML 排版预览？”，并解释两种交付差异。只有用户已明确选择，或明确说“不要询问”“直接处理”“自动匹配”时，才跳过询问并采用平台默认值。

各平台的必要询问按 `platform-native-protocol.md` 的矩阵执行：公众号确认排版主题，知乎确认回答 / 专栏与是否预览，小红书确认纯文本笔记/手机卡片与笔记气质，官网/网页确认网页结构、内容目标和发布环境，个人博客确认 Markdown/CMS/静态 HTML 与博客长文风格。多个缺口一次合并，不逐项来回打断。

## 二、基础交付物

进入文件交付时，所有平台先具备：

1. **标题策略 Markdown**：`title-strategy.md`，包含推荐/主标题、至少 2 个备选标题和简短选择理由；标题形态必须符合目标平台。
2. **平台原生正文**：使用平台可直接发布或继续编辑的格式，例如 `article-source.md`、`zhihu-source.md`、`note-source.txt`、`web-source.md`。

用户只要求聊天内快速回答、没有要求文件时，可以直接在对话中交付，不为了凑文件强制创建目录和附件。

## 三、涉及排版时增加两个 HTML

只要本次交付包含排版，不论平台，都在基础交付物上增加：

3. **干净排版 HTML**：只包含平台适配后的正文与样式，不带复制工具栏，适合预览、发布或手动处理。
4. **复制预览 HTML**：浏览器可打开，带明确复制按钮；复制内容必须符合平台口径。

复制口径：

- 公众号：复制渲染后的富文本 HTML。
- 知乎：复制适合回答 / 专栏编辑器的正文，优先保持标题层级、列表和引用。
- 小红书：复制纯文本笔记，不复制网页卡片样式。
- 官网/网页：复制网页正文；干净 HTML 可直接进入网页开发或 CMS 流程。
- 个人博客：根据 Markdown、富文本或静态 HTML 的发布方式选择复制目标。

非公众号平台需要排版时，使用：

```bash
python3 scripts/build_html.py <平台原文> -o article.html --platform <平台> --emit-pair
python3 scripts/validate_delivery_bundle.py <交付目录> --platform <平台> --layout
```

## 四、公众号固定四件套

公众号完成写作与排版后，以下四件全部必选，不得按模型判断省略：

1. `title-strategy.md`：标题策略。
2. `article-source.md`：正文 Markdown 原稿。
3. `article-gzh.html`：**公众号正文 HTML**，保持干净、可粘贴。
4. `article-preview.html`：**复制预览 HTML**，带“复制到公众号”功能。

生成完成后必须运行：

```bash
python3 scripts/validate_delivery_bundle.py <交付目录> --platform 公众号
```

公众号天然进入排版模式，因此不需要额外传 `--layout`。少任何一件都不能交付。

## 五、生成阶段

1. 在当前 workspace 的任务目录中生成文件，不写入临时聊天缓存目录。
2. 文件名优先使用短 ASCII 名称，避免跨系统编码问题。
3. HTML 内部资源使用相对路径；单文件预览将必要样式和可嵌入资源写入同一 HTML。
4. 标题/金句换行、强调句换行要先按语义设计，再交给浏览器渲染，适用于所有主题和所有平台预览。封面标题、目录卡标题、公式句、引用金句、提示句和居中大字不得出现末行只剩 1-3 个字、一个标点或半个词；必要时缩短、主动分行或改两段式表达。短金句、短公式、短判断可以居中；长解释、人物说法、多句引用或接近段落的内容必须左对齐自然换行。渲染器应对过长居中强调块做左对齐兜底。
5. 前端标签白名单只使用读者能理解的内容标签，例如实用指南、行动清单、信息指南、时间提醒、深度解读、判断参考、避坑提醒、案例复盘、经验总结。不要在读者端暴露“中立、客观中立、模型生成、提示词、公众号排版、深度文章、内部标签”等编辑后台词或生产词。
6. 检查每个文件存在、非空、可读。HTML 还要确认浏览器可打开、正文非空、复制按钮不遮挡正文。
7. 标题策略、原文、干净 HTML 和复制预览必须来自同一最终版本，不能交付版本互相不一致的文件。

## 六、附件优先级

1. 调用宿主提供的原生附件、文件卡片、artifact 或等价能力。
2. 有复制预览时先附预览，再附干净 HTML、平台原文和标题策略；无排版时先附平台原文，再附标题策略。
3. 最终回复中的说明与附件名称一一对应，不生成一个名字、附上另一个文件。
4. 若宿主能回读附件状态，确认消息中已出现文件卡片后再结束。

## 七、禁止做法

- 不把 Windows 或 macOS 本地绝对路径写成 Markdown 链接，例如 `[预览](D:\\work\\article.html)` 或 `[预览](/Users/name/article.html)`。
- 不把不存在的路径、旧文件、临时文件或另一个环境中的文件包装成蓝色链接。
- 不因链接文字显示为蓝色就声称“可以直接打开”。
- 不把公众号富文本复制方式用于小红书。
- 不把“公众号固定四件套”写成所有平台固定四件套。
- 不因标题策略已经出现在聊天文字里，就在正式文件交付中省略标题策略文件。

## 八、能力降级

宿主没有原生附件/文件卡片能力时：

1. 明确说明当前宿主不支持把本地文件作为可点击附件发送。
2. 以纯文本列出真实绝对路径、文件名和用途，不使用 Markdown 链接。
3. 给出最短打开方式，但不让用户误以为链接可点击。

能力降级是事实说明，不得掩饰。Skill 能统一交付决策，但不能替宿主凭空增加附件能力。
