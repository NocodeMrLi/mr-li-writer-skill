# 跨平台、跨宿主交付协议

## 目标

交付物由发布平台的真实编辑与发布方式决定，不把公众号四件套复制到所有平台。进入文件交付时，先保证标题和平台原生正文可直接使用；只有平台属性或用户要求涉及排版，才增加两个 HTML 文件。

无论运行在 Codex、WorkBuddy、Claude Code、Cursor 或其他宿主中，交付物都必须先是一个真实文件，再作为宿主原生附件或文件卡片出现。蓝色文字不等于附件，可点击承诺必须有宿主能力、实际文件、成功的附件调用和逐文件附件回执共同支撑。文件任务在任务页出现可点击文件卡片、终态门禁输出 `DELIVERY_COMPLETE` 前，不得把任务标记为已交付。

## 一、先做交付判断

进入任何交付判断前，必须已有通过 `scripts/validate_task_intake.py` 生成或校验过的任务状态。没有 `--task-state`，正式 HTML 生成和交付校验会阻断；这用于防止模型把推荐项、历史默认或“继续任务”误当成用户确认。

内部记录：

```text
- 发布平台：
- 平台原生正文格式：Markdown / 纯文本 / HTML
- 是否需要排版：是 / 否
- 判断依据：平台必需 / 用户明确要求 / 系统自动匹配
- 复制目标：富文本 HTML / 平台纯文本 / Markdown
```

当用户没有指定时，按平台属性判断：

| 发布平台 | 平台原生正文 | 默认是否排版 | 交付规则 |
| :--- | :--- | :--- | :--- |
| 公众号 | Markdown 原稿 + 公众号富文本 | 是，必需 | 固定四件套 |
| 知乎 | 回答 / 专栏 Markdown 或纯文本 | 否 | 默认标题策略 + 知乎原文；要求预览时再加两个 HTML |
| 小红书 | 可直接发布的纯文本笔记 | 否 | 默认标题策略 + 笔记原文；要求手机卡片预览时再加两个 HTML，复制页复制纯文本 |
| 官网/网页 | Markdown 源稿 + 网页 HTML | 是 | 标题策略、网页源稿、干净网页 HTML、复制预览 HTML |
| 个人博客 | 取决于博客系统 | 条件式 | Markdown 博客默认两件；静态 HTML/排版要求时增加两个 HTML |

未知平台先判断它接收纯文本、Markdown、富文本还是网页文件。无法确认且用户也未要求排版时，优先交付标题策略和平台原生正文，不机械生成 HTML。

知乎和小红书不能直接用表格中的默认值静默执行。用户未说明排版需求时，先询问“是否需要 HTML 排版预览？”，并解释两种交付差异。只有用户已明确选择，或明确说“不要询问”“直接处理”“自动匹配”时，才跳过询问并采用平台默认值。

各平台的必要询问按 `platform-native-protocol.md` 的矩阵执行：公众号确认排版主题，知乎确认回答 / 专栏与是否预览，小红书确认纯文本笔记/手机卡片与笔记气质，官网/网页确认网页结构、内容目标和发布环境，个人博客确认 Markdown/CMS/静态 HTML 与博客长文风格。同一依赖阶段的多个缺口合并确认；平台未知时先选平台，下一阶段再问该平台样式。

## 二、基础交付物

进入文件交付时，所有平台先具备：

1. **标题策略 Markdown**：`title-strategy.md`，包含推荐/主标题、至少 2 个备选标题和简短选择理由；标题形态必须符合目标平台。
2. **平台原生正文**：使用平台可直接发布或继续编辑的格式，例如 `article-source.md`、`zhihu-source.md`、`note-source.txt`、`web-source.md`。

用户只要求聊天内快速回答、没有要求文件时，可以直接在对话中交付，不为了凑文件强制创建目录和附件。

## 三、涉及排版时增加两个 HTML

只要本次交付包含排版，不论平台，都在基础交付物上增加：

3. **干净排版 HTML**：只包含平台适配后的正文与样式，不带复制工具栏，适合预览、发布或手动处理。
4. **复制预览 HTML**：浏览器可打开，带明确复制按钮；复制内容必须符合平台口径。

复制口径：

- 公众号：复制渲染后的富文本 HTML。
- 知乎：复制适合回答 / 专栏编辑器的正文，优先保持标题层级、列表和引用。
- 小红书：复制纯文本笔记，不复制网页卡片样式。
- 官网/网页：复制网页正文；干净 HTML 可直接进入网页开发或 CMS 流程。
- 个人博客：根据 Markdown、富文本或静态 HTML 的发布方式选择复制目标。

非公众号平台需要排版时，使用：

```bash
python3 scripts/build_html.py <平台原文> -o article.html --platform <平台> --emit-pair --task-state <任务状态.json>
python3 scripts/validate_delivery_bundle.py <交付目录> --platform <平台> --layout --task-state <任务状态.json>
```

## 四、公众号固定四件套

公众号完成写作与排版后，以下四件全部必选，不得按模型判断省略：

1. `title-strategy.md`：标题策略。
2. `article-source.md`：正文 Markdown 原稿。
3. `article-gzh.html`：**公众号正文 HTML**，保持干净、可粘贴。
4. `article-preview.html`：**复制预览 HTML**，带“复制到公众号”功能。

生成完成后必须运行：

```bash
python3 scripts/validate_delivery_bundle.py <交付目录> --platform 公众号 --task-state <任务状态.json>
```

公众号天然进入排版模式，因此不需要额外传 `--layout`。少任何一件都不能交付。

正式公众号文件还必须满足同源合同：干净 HTML 带完整组件库渲染器与真实主题标识；复制预览由官方模板生成，使用 `ClipboardItem` 同时写入 `text/html` 和 `text/plain`，不得用 `writeText(innerHTML)`；预览内正文、摘要与干净 HTML 必须完全一致。任何 Agent 或模型都不得手写一个同色简化页冒充主题组件库，也不得自行拼复制脚本。校验失败时回到 `build_gzh_html.py` 重新生成，不通过“补字符串”伪造合格产物。

## 五、生成阶段

1. 在当前 workspace 的任务目录中生成文件，不写入临时聊天缓存目录。
2. 文件名优先使用短 ASCII 名称，避免跨系统编码问题。
3. HTML 内部资源使用相对路径；单文件预览将必要样式和可嵌入资源写入同一 HTML。
4. 标题/金句换行、强调句换行要先按语义设计，再交给浏览器渲染，适用于所有主题和所有平台预览。封面标题、目录卡标题、公式句、引用金句、提示句和居中大字不得出现末行只剩 1-3 个字、一个标点或半个词；必要时缩短、主动分行或改两段式表达。短金句、短公式、短判断可以居中；长解释、人物说法、多句引用或接近段落的内容必须左对齐自然换行。渲染器应对过长居中强调块做左对齐兜底。
5. 前端标签白名单采用严格读者口径，不采用“发现一个禁词再补一个”的黑名单策略。可根据内容使用实用指南、行动清单、信息指南、时间提醒、最新消息、考试动态、政策动态、行业观察、前沿观察、深度解读、判断参考、选择参考、避坑提醒、案例复盘、经验总结等；“最新消息”必须有最新核验。未进入白名单的内部能力名、编辑后台词、生产词或立场词一律回退为匹配正文的读者标签。
6. 检查每个文件存在、非空、可读。HTML 还要确认浏览器可打开、正文非空、复制按钮不遮挡正文。
7. 标题策略、原文、干净 HTML 和复制预览必须来自同一最终版本，不能交付版本互相不一致的文件。
8. 公众号预览按钮复制的是浏览器已渲染的富文本，不是 HTML 字符串；135 编辑器或公众号草稿箱中出现 `<section style=...>`、`<!--p...-->` 等源码时，视为阻断性失败，必须停止交付并重新生成。

## 六、附件优先级

1. 必须调用宿主提供的原生附件、文件卡片、artifact 或等价能力；这不是可选的展示优化，而是文件交付的完成条件。
2. 有复制预览时先附预览，再附干净 HTML、平台原文和标题策略；无排版时先附平台原文，再附标题策略。
3. 最终回复中的说明与附件名称一一对应，不生成一个名字、附上另一个文件。
4. 检查 attachment tool result；若宿主能回读附件状态，确认消息中已出现文件卡片后再结束。

## 七、可点击交付硬门禁

1. 首次运行交付校验器后，按 `ATTACHMENT_REQUIRED` 输出顺序调用附件工具。文件合格时校验器输出 `DELIVERY_PENDING` 并以退出码 `3` 结束；这表示必须继续，不表示失败，更不表示完成。
2. 有预览 HTML 时，预览 HTML 必须作为第一张文件卡片。用户可以直接点击打开预览，然后再按需打开干净 HTML、平台原文和标题策略。
3. 仅列出工作区路径不算交付；代码样式文件名、Markdown 本地链接、文件清单表格和“请到工作区打开”都不能替代文件卡片。
4. 只有附件工具返回成功，且可回读时已确认文件卡片出现，才能形成附件回执。回执必须逐文件记录工具返回的唯一引用，不能在调用工具前手写，也不能把路径或文件名填进 `delivery_ref`。
5. 使用 `--attachment-receipt <附件回执.json>` 再运行交付校验器。只有输出 `DELIVERY_COMPLETE` 且退出码为 `0`，才能说“已交付”“可点击打开”或结束文件任务。
6. 附件调用失败时，用短 ASCII 文件名和 workspace 内实际文件重试一次。仍失败则明确报告宿主能力阻断并保持 `DELIVERY_PENDING`；不得给出目录、路径、文件名清单或“去工作区查找”作为替代交付。

附件回执 schema：

```json
{
  "schema_version": 1,
  "host": "workbuddy",
  "artifacts": [
    {
      "role": "复制预览 HTML",
      "path": "<ATTACHMENT_REQUIRED 中的真实文件绝对路径>",
      "sha256": "<附件调用时该文件的 SHA-256>",
      "status": "attached",
      "openable": true,
      "verification": "tool_success",
      "delivery_ref": "<附件工具真实返回的非本地唯一引用>"
    }
  ]
}
```

`artifacts` 必须与 `ATTACHMENT_REQUIRED` 数量、角色和顺序完全一致。`verification` 只能是 `tool_success` 或 `ui_readback`；能回读任务页时优先使用 `ui_readback`。每个 `delivery_ref` 必须唯一，并且不能是 `file:`、Windows/macOS/Linux 本地路径、文件名或 Markdown 本地链接。

## 八、禁止做法

- 不把 Windows 或 macOS 本地绝对路径写成 Markdown 链接，例如 `[预览](D:\\work\\article.html)` 或 `[预览](/Users/name/article.html)`。
- 不把不存在的路径、旧文件、临时文件或另一个环境中的文件包装成蓝色链接。
- 不因链接文字显示为蓝色就声称“可以直接打开”。
- 不把公众号富文本复制方式用于小红书。
- 不把“公众号固定四件套”写成所有平台固定四件套。
- 不因标题策略已经出现在聊天文字里，就在正式文件交付中省略标题策略文件。

## 九、能力阻断

宿主没有原生附件/文件卡片能力时：

1. 明确说明当前宿主不支持把本地文件作为可点击附件发送，因此本次可点击交付未完成。
2. 保持 `DELIVERY_PENDING`，不得输出目录、真实绝对路径、代码样式文件名、文件清单或“去右侧工作区查找”作为交付替代品。
3. 不得使用“文章已完成”“交付校验通过”“已生成交付文件”等会让用户误以为任务已完成的表述；等待宿主开放原生附件能力或切换到支持附件的会话后再继续。

能力阻断是事实说明，不得掩饰。Skill 能统一交付决策，但不能替宿主凭空增加附件能力；没有原生附件能力时，只能诚实保留 `DELIVERY_PENDING`，不能用路径清单制造“已经交付”的假象。
