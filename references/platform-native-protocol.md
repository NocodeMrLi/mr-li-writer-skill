# 平台原生内容与交付规范

## 总原则

发布平台和内容目标必须分开判断。

发布平台回答“内容最终发在哪里”；内容目标回答“这篇内容要达成什么”。不要把 `SEO`、`GEO` 当成发布平台。更合理的默认分类是：

发布平台：

- 公众号
- 知乎
- 小红书
- 官网/网页
- 个人博客

内容目标：

- 普通传播
- GEO / 生成式搜索优化
- SEO / 搜索引擎优化
- 转化销售
- 专业报告

平台决定表达形态、标题语气、正文结构、交付样式和复制方式；内容目标决定关键词、来源、FAQ、转化动作和信息完整度。

## 最低必要询问

询问是为了避免交付预期错位，不是给每个任务增加问卷。先读取用户已经提供的信息，只问会改变正文形态、标题策略或交付文件的问题；已经明确的信息不重复询问。多个必要缺口应一次合并询问，通常不超过 3 个短问题。

确认分三层：

- **必问**：发布平台、内容目标、创作方向、平台交付样式。
- **条件问**：目标读者/阅读场景、立场边界、时效口径、来源边界、交付格式、篇幅深度。
- **不默认问**：语气风格、开头方式、标题数量、是否要金句、是否要案例。

不默认问不是不处理，而是由系统按平台、体裁和读者任务内部判断。用户主动指定偏好时必须尊重。

### 必要询问矩阵

| 场景 | 用户未说明时必须确认 | 可以不问的情况 |
| :--- | :--- | :--- |
| 未指定发布平台 | 内容最终发布到哪里 | 用户只要通用草稿，或授权系统自动匹配 |
| 未指定内容目标 | 普通传播、SEO/GEO、转化销售还是专业报告 | 用户只要快速草稿且无搜索、转化、报告线索时可默认普通传播 |
| 创作方向不明确 | 给 3-5 个方向候选并标注最推荐、次推荐 | 用户已明确方向，或授权系统按最推荐方向继续 |
| 公众号 | 公众号排版主题；可给系统推荐主题，但必须让用户确认 | 用户已指定主题，或说“直接排/自动匹配” |
| 知乎 | 写回答还是专栏；是否需要 HTML 排版预览 | 问题语境已明确是回答；样式选择已明确或授权自动匹配 |
| 小红书 | 清爽纯文本笔记还是手机卡片预览；偏种草、避坑或收藏清单 | 用户已明确只要纯文本/需要卡片，或授权自动匹配 |
| 官网/网页 | 普通网页文章、SEO-GEO 结构化、转化落地页还是专业报告页；发布环境是否有模板/CMS 约束 | 用户已给内容目标、发布环境和样式要求；只需通用单文件网页且授权自动匹配 |
| 个人博客 | 发布格式是 Markdown / CMS 富文本 / 静态 HTML；博客长文气质 | 用户已说明博客系统、输出格式或授权自动匹配 |
| 未知平台 | 平台接收纯文本、Markdown、富文本还是 HTML | 用户已给可发布格式 |

官网/网页的“内容目标”和“发布环境”会直接改变标题、FAQ、元数据和 HTML 形态，因此缺失时应询问；不能把 SEO/GEO 当成默认。每个平台都要确认会改变最终产物的交付样式：公众号确认主题，知乎确认回答 / 专栏与预览，小红书确认纯文本 / 卡片和笔记气质，官网确认网页结构，博客确认发布格式。用户只确认“平台”和“创作方向”不等于确认交付样式；样式未确认前，不得把具体样式写入任务列表或生成最终文件。知乎若标题本身是明确问题，可以直接按回答处理，但仍需确认是否需要 HTML 预览。

如果同一任务同时缺发布平台、内容目标和交付格式，使用一次合并询问，例如：

```text
开始前确认 3 点：
1. 发布到哪个平台？
2. 主要目标是普通传播、SEO/GEO、转化还是专业报告？
3. 平台交付样式用哪个？例如公众号主题、知乎预览、小红书卡片、网页结构或博客格式。
```

用户明确说“不要询问”“直接处理”“自动匹配”时，记录授权并采用平台默认值，同时在最终交付中说明实际选择。

### 必问项与条件触发项硬门禁

必问项和已触发的条件触发项决定正文形态、排版方式、核验边界和交付文件，因此不是建议项。必问项缺失时不得写正文、生成任务列表、创建文件、排版或交付；条件触发项一旦被触发，就临时升级为本任务的必确字段，确认前不得进入下一阶段。

硬门禁字段：

- 必问项：发布平台、内容目标、创作方向、平台交付样式。
- 条件触发项：目标读者/阅读场景、立场边界、时效口径、来源边界、交付格式、篇幅深度。

执行要求：

- 不得用模型推断、历史默认、平台默认或推荐项替代用户确认。
- 不得把用户对一个字段的确认扩展解释为其他字段也已确认。
- 不得因为已经生成过一版正文，就跳过后续应补齐的确认。
- 条件触发项被触发时，先合并进下一次确认；不能把它当作内部可选优化。
- 用户明确说“自动匹配 / 不用问 / 直接处理 / 直接排”时，才允许系统补齐默认值，并在交付说明中写清采用了哪些默认项。

### 恢复任务防误判

当用户在 token 中断、模型切换、上下文压缩、长任务恢复或宿主重试后说“继续”“接着做”“继续完成任务”“恢复任务”“按刚才的来”等指令时，必须先做状态校验，不得把“继续”理解为用户已确认缺失项。

恢复前检查：

- 发布平台、内容目标、创作方向、平台交付样式是否已明确。
- 如果是公众号，具体主题是否已确认，或用户是否明确授权自动匹配。
- 如果是知乎或小红书，平台形态和是否需要 HTML 预览是否已确认。
- 如果是官网/网页或个人博客，网页结构、发布环境、CMS/Markdown/HTML 格式是否已确认。
- 如果是时效、政策、考试、价格、版本、榜单类内容，信息截至时间和来源边界是否已确认或已完成最新核验。

只要任一必问项或触发的条件问缺失，就先补问，不能直接创建任务列表、写正文、选主题、生成 HTML 或交付文件。推荐开场：

```text
我先恢复一下当前状态：前面任务被中断了，目前还缺这些必要信息，确认后我再继续执行。
```

只有用户明确回复“自动匹配 / 不用问 / 直接继续”时，才允许系统按默认策略补齐缺失项，并在最终交付说明中写清采用了哪些默认值。

### 条件询问触发

| 条件项 | 触发场景 | 处理方式 |
| :--- | :--- | :--- |
| 目标读者/阅读场景 | 主题宽泛、可能写给不同人群 | 在方向候选中体现人群差异，必要时询问 |
| 立场边界 | 观点、评论、评测、争议话题 | 确认锋利/保守、是否允许批评和反方展开 |
| 时效口径 | 政策、考试、报名、价格、产品更新、榜单 | 确认或自动执行最新核验，并标明信息截至时间 |
| 来源边界 | 证书、政策、医疗、法律、金融、教育培训、商业评测 | 优先官方来源，第三方只作辅助核对 |
| 交付格式 | 知乎、小红书、博客、官网/网页、未知平台 | 问清纯文本、Markdown、富文本、HTML 或复制预览 |
| 篇幅深度 | 同题可短可长，或深度影响研究成本 | 给短文/标准/深度选择，用户不选时采用平台默认 |

### 知乎与小红书排版确认

选择知乎或小红书后，如果用户尚未说明是否需要排版，必须在 brief 阶段主动询问：

```text
是否需要 HTML 排版预览？
1. 不需要：交付标题策略 + 平台原文。
2. 需要：再增加干净 HTML + 带复制功能的 HTML。
```

不能因为平台默认使用原生文本就静默省略询问。用户授权自动匹配时，知乎与小红书采用原生文本交付；如果正文含复杂表格、图文说明或用户明显需要可视化预览，可以自动选择排版，并在交付说明中写清楚。

## 平台分支

### 公众号

公众号可以生成完整文章。重点是开头钩子、叙事节奏、观点判断、读者共鸣和可读排版。

推荐结构：

```text
开头入口 -> 核心判断 -> 2-4 个展开段落 -> 反方/边界 -> 结尾回收
```

交付样式：

- 公众号内联 HTML 正文片段
- 带“复制到公众号”按钮的预览页
- 主题池：`moyu-green`、`red-white`、`graphite-minimal`、`zen-whitespace`、`moyu-ticket`、`olive-journal`
- 主题选择：用户没指定时先推荐；用户说“直接排”“不用问”时自动匹配
- 脚本约束：正式生成公众号 HTML 时必须使用已确认的 `-t <主题名> --theme-confirmed`；只有用户明确授权自动匹配时，才可使用 `-t auto --auto-theme-ok` 或 `-t random --auto-theme-ok`
- 复制方式：预览页复制渲染后的富文本，方便粘贴到公众号编辑器

### 知乎

知乎要像真实回答或专栏文章。标题可以是问题，也可以是明确判断型专栏标题。

推荐结构：

```text
短结论 -> 适用边界 -> 论证和反例 -> 具体建议 -> 总结判断
```

要求：

- 开头先给短结论，不做公众号式铺垫。
- 正文有论证、边界、反例和适用人群。
- 避免营销腔、煽动标题和情绪化号召。

交付样式：

- 问答 / 专栏样式
- 默认交付符合知乎编辑逻辑的 Markdown/纯文本原文，不强制生成 HTML。
- 用户要求排版或预览时，增加干净 HTML 与带复制功能的 HTML；复制内容仍以知乎回答 / 专栏正文为准。

### 小红书

小红书不是公众号文章缩略版，而是平台原生笔记。发布平台选择“小红书”时，必须进入独立生成分支，不能沿用公众号、知乎、博客的完整长文逻辑。

生成要求：

- 写一篇小红书笔记，不写公众号长文，也不只是把长文缩短。
- 一级标题用最适合发布的笔记标题，短、具体、有场景。
- 开头 1-2 句直接给钩子或结论。
- 正文用 4-8 个短段或清单，每段尽量 1-3 行。
- 克制使用 emoji 或符号化段落提示，至少出现 3 个，但不要满屏表情。
- 必须包含“适合谁 / 不适合谁 / 避坑 / 判断标准 / 可收藏清单”中的至少两个模块。
- 不使用公众号式铺垫、宏大背景、报告腔长段落。
- 末尾必须有“标签”区域，给 6-10 个小红书话题标签，以 `#` 开头。

推荐结构：

```text
# 短标题

1-2 句钩子 / 结论

✅ 适合谁
...

⚠️ 不适合谁 / 避坑
...

📌 判断标准 / 可收藏清单
...

标签
#话题 #话题 #话题
```

写作口径：

- 口语化，但不装熟。
- 信息要可收藏、可执行、可转发给朋友。
- 句子短，段落短，信息密度高。
- 允许 emoji，但 emoji 是段落提示，不是装饰噪音。
- 不写“本文将从三个方面展开”“综上所述”“随着时代发展”。

交付样式：

- 默认：清爽纯文本笔记，可直接复制发布。
- 预览：手机笔记卡片，仅在用户要求或系统确认需要视觉预览时生成。
- 复制方式：纯文本优先，不复制公众号富文本 HTML。

### 官网/网页

官网/网页是发布平台，SEO/GEO 是内容目标。网页文章可以更结构化，适合长期检索、品牌介绍、解决方案、帮助中心和专题页。

当内容目标为 GEO：

- 结论前置。
- 实体名称清楚。
- 小标题尽量问题化。
- 增加 FAQ。
- 保留可验证来源。
- 避免只写情绪化观点。

当内容目标为 SEO：

- 明确搜索意图。
- 覆盖主关键词、长尾问题和相关问法。
- 增加 FAQ、摘要和参考资料。
- 不编造搜索量、排名概率和流量承诺。

交付样式：

- 网页文章 / SEO-GEO 结构化样式。
- 官网/网页的 HTML 是发布形态的一部分，默认交付标题策略、网页源稿、干净 HTML 与带复制功能的 HTML；不能因为 HTML 可直接发布就省略原文和标题策略。

### 个人博客

个人博客可以保留作者判断、长线观察和更完整的解释，但仍要避免公众号式煽动和 SEO 堆砌。

交付样式：

- 默认先交付博客 Markdown 原文。
- 用户使用静态博客、需要 HTML 发布或明确要求排版时，再生成干净 HTML 与带复制功能的 HTML。

## 平台交付样式

用户没有指定交付样式时，根据发布平台给出推荐选项并让用户确认；用户明确说“自动匹配 / 直接处理 / 不用问”时，才静默采用默认。

### 平台交付样式硬确认

发布平台一旦确定，就必须在写正文、生成任务列表、创建正文文件、生成 HTML 或交付文件之前确认平台交付样式。这个规则覆盖公众号、知乎、小红书、官网/网页、个人博客和未知平台；不得把它理解成只适用于公众号。

执行要求：

- 必须完整展示该平台的全部可选交付样式，并标出推荐项；不得只展示推荐项。
- 宿主选择器如果不能放下全部选项，必须在正文消息中完整列出全部选项，让用户用编号、名称或“自动匹配”回复。
- 用户只确认平台、创作方向、正文方向、标题策略或“正文没问题”，不等于确认平台交付样式。
- 推荐样式、系统判断、上一轮默认值都不等于用户确认。
- 除非用户明确说“自动匹配 / 不用问 / 直接处理 / 直接排”，否则不得替用户选择平台交付样式。
- 平台交付样式未确认前，不得生成带具体样式的任务列表，不得创建正文文件，不得进入排版或交付。
- “主题”只用于文章主题；涉及公众号排版时必须写“公众号排版主题”，避免模型把文章主题和排版主题混淆。

| 发布平台 | 推荐样式 | 可选样式 |
|---|---|---|
| 公众号 | 根据内容推荐 1 个公众号主题 | 摸鱼绿、红白色系、石墨极简风、留白禅意风、摸鱼票据风、橄榄手记、自动匹配 |
| 知乎 | 回答 / 专栏原文 | 回答 / 专栏、是否增加 HTML 预览与复制页 |
| 小红书 | 清爽纯文本笔记 | 手机卡片预览、偏种草、偏避坑、偏收藏清单、自动匹配 |
| 官网/网页 | 网页文章或 SEO-GEO 结构化样式 | 普通网页、SEO-GEO 结构化、转化落地页、专业报告页、CMS/模板适配 |
| 个人博客 | Markdown 博客长文 | CMS 富文本、静态 HTML、作者随笔、技术长文、观点札记、自动匹配 |

用户手动指定交付样式时，尊重用户选择，但如果选择明显不适配平台，要提醒风险。例如：小红书选择公众号富文本 HTML，会导致复制和发布口径不匹配。

交付文件数量不预先固定。进入文件交付时，标题策略和平台原生正文是基础；只有本次涉及排版时才增加干净 HTML 和复制预览 HTML。公众号因平台发布流程固定要求排版，所以始终为四件套；其他平台按上表和用户需求决定。

## 小红书质检

发布平台为小红书时，交付前检查：

- 是否至少有 3 个 emoji 或符号化段落提示。
- 是否有 6-10 个 `#` 话题标签。
- 是否存在多个过长段落。
- 是否包含“适合谁 / 不适合谁 / 避坑 / 判断标准 / 可收藏清单”中的至少两个模块。
- 是否出现公众号腔、长文铺垫、报告腔。
- 是否只是把公众号文章缩短，而没有重写标题、开头、结构、段落节奏和标签。

发现问题后直接改正文，再重新检查。不要把问题列表直接交给用户作为最终交付。
